# 通信十六进制数据格式汇总（项目内实际使用）

本项目的前端通过 WebSocket 与网关通信，网关再与实物设备交互。数据在 WebSocket 层都是 **16 字节的二进制帧**，在调试界面中以 **十六进制字符串** 展示或手动构造。

下面按「帧结构」「数据类型」「传感器查询」「执行器控制」四部分汇总。

---

## 一、16 字节工业协议帧整体结构

- 帧长度：固定 16 字节
- 字节布局（索引从 0 开始）：
  - Byte 0：帧头 `head`
    - `0xCC`：PC → 节点（下行）
    - `0xBB`：节点 → PC（上行）
  - Byte 1：长度 `length`
    - 项目中固定为 `0x10`（16）
  - Byte 2：主类型 `mainType`
    - 见「设备主类型」
  - Byte 3：子类型高字节 `subTypeHigh`
  - Byte 4：子类型低字节 `subTypeLow`
    - 两者组合成 16 位子类型：`subType = (subTypeHigh << 8) | subTypeLow`
  - Byte 5：设备索引 `index`
  - Byte 6：命令字 `cmd`
    - `0x01`：控制（CONTROL）
    - `0x02`：查询（QUERY）
    - `0x03`：上报（REPORT）
  - Byte 7：数据类型 `dataType`
    - `0x01`：BOOL
    - `0x02`：INT
    - `0x03`：FLOAT
    - `0x04`：ARRAY
    - `0x05`：STRING
  - Byte 8–13：数据区 `data[0..5]`（6 字节）
  - Byte 14–15：CRC 校验 `verification`
    - 协议为 **Modbus CRC16**，多项式 `0xA001`
    - 计算时对前 14 字节 (`buffer[0..13]`) 进行 CRC：
      - 低字节放在 Byte 14，高字节放在 Byte 15

## 二、设备主类型、子类型与物理含义

### 1. 主类型（DeviceMainType）

- `0x01`：IO
- `0x02`：POWER_CONTROL
- `0x03`：COMMUNICATION
- `0xFF`：DEFAULT

### 2. 部分已使用子类型映射（SENSOR_TYPE_BY_MAIN）

- 主类型 `0x01`（IO）：
  - `0x0001`：烟雾（smoke）
  - `0x0003`：人体（human / PIR）
  - `0x0004`：雨雪（rainSnow）
  - `0x000A`：土壤湿度（soilHumidity）
  - `0x000B`：土壤温度（soilTemperature）
- 主类型 `0x03`（COMMUNICATION）：
  - `0x0001`：光照（light）
  - `0x0002`：空气温度（airTemperature）
  - `0x0003`：空气湿度（airHumidity）
  - `0x000A`：CO₂（co2）
  - `0x000D`：风速（windSpeed）
  - `0x000E`：风向（windDirection）
  - `0x000F`：pH（ph）

在仪表盘中，`SENSOR_DEVICES` 与这些主/子类型对应，用来识别上行报文并显示数值。

## 三、数据区 6 字节格式约定（createPayload）

项目中用一个 6 字节的 payload 作为数据区（Byte 8–13），不同的数据类型具体编码如下：

### 1. BOOL（DataType.BOOL，值 0x01）

- 长度：6 字节
- 含义：
  - `data[5] = 1` 表示 `true`
  - `data[5] = 0` 表示 `false`
  - 其余字节为 0

### 2. 控制字节（controlByte，用于某些控制型命令）

- 长度：6 字节
- 含义：
  - 取整后的数值 `v = floor(val)`，写入：
    - `data[5] = v & 0xFF`
  - 其余字节为 0

### 3. 有符号整型（INT，DataType.INT，值 0x02）

- 长度：6 字节
- 编码方式：
  - `data[0]`：符号位
    - `0`：非负
    - `1`：负数
  - `data[1..4]`：32 位无符号整数的高位在前（Big Endian）
    - 存的是绝对值 `abs(val)` 的整数部分
  - `data[5]`：未使用（0）

### 4. 浮点型放大整数（FLOAT，DataType.FLOAT，值 0x03）

- 长度：6 字节
- 编码方式：
  - 将浮点数放大 10000 倍并取整：`scaled = round(val * 10000)`
  - `data[0]`：符号位（同 INT）
  - `data[1..4]`：`abs(scaled)` 的无符号 32 位整数（Big Endian）
  - `data[5]`：未使用（0）

> 注：协议层不使用 IEEE 754 直接编码，而是「放大 + 整数」的方式，便于在 MCU 端解析和保持精度。

## 四、传感器查询报文格式（手动/自动刷新）

在协议仪表盘中，「手动查询」和「自动刷新」均通过 `packFrame` 构造查询帧，然后通过 WebSocket 发送。

### 1. 查询帧构造规则

- `head = 0xCC`（PC → 节点）
- `length = 0x10`（内部固定）
- `addr`：
  - `mainType`：来自 `SENSOR_DEVICES[i].mainType`
  - `subTypeHigh` / `subTypeLow`：来源于 `SENSOR_DEVICES[i].subType`
  - `index`：`SENSOR_DEVICES[i].index ?? 0`
- `cmd = 0x02`（QUERY）
- `dataType = BOOL`（0x01）：
  - 对于查询命令，当前实现中使用一个全 0 的 6 字节数组：
    - `data = [0, 0, 0, 0, 0, 0]`
- CRC 按前述规则计算。

### 2. 响应帧（节点 → PC）

- `head = 0xBB`
- 其他字段（mainType、subTypeHigh/Low、index）与请求对应。
- `cmd = 0x03`（REPORT）
- `dataType` 和 `data` 取决于设备类型：
  - 布尔量传感器：通常为 `BOOL`
  - 数值类传感器（温度、湿度、光照、CO₂ 等）：多为 `FLOAT` 或 `INT`，按协议解析。
- 前端通过：
  - `unpackFrame()` 校验 CRC 并解析帧；
  - `getSubType()` 组合子类型；
  - `decodeFrameValue()` 将 data 字节转成实际数值；
  - 映射到 `SENSOR_DEVICES` 中对应的设备 ID，并更新界面。

## 五、执行器控制报文格式与项目中使用的所有十六进制指令

执行器控制有两种来源：

1. **通用控制报文**：通过 `packFrame + createPayload` 构造（当前项目主要用于查询，控制暂未直接用到）。
2. **写死的 16 字节十六进制指令**：在 `ACTUATOR_DEVICES` 中，以字符串方式配置。

这里重点汇总第二种：项目中实际使用的 **所有执行器控制十六进制指令**。

### 1. 字符串到帧的转换规则（hexToFrame）

- 在 `protocolDashboardApp.tsx` 中，通过 `hexToFrame` 将字符串转为 `Bytes`：
  - 先去除所有非 16 进制字符（空格等）；
  - 要求最终长度为 32 个 hex 字符（16 字节）；
  - 每两个字符组合为一个字节，按顺序填入 16 字节数组。
- 这些帧随后直接通过 WebSocket 发送（`socket.send(frame.buffer)`），并记录在协议监视器中。

### 2. 所有执行器及对应的十六进制控制帧

以下每一条都是一个完整的 16 字节帧（包含头、地址、命令、数据和 CRC）。

- 设备信息：

  - `index = 0x00`
- 指令：
  - 打开：
    - `CC 10 03 00 A2 00 01 04 00 00 00 00 AA A9 C0 C3`
  - 关闭：
    - `CC 10 03 00 A2 00 01 04 00 00 00 00 AA A8 01 03`

## 六、调试与扩展建议

- 如需新增设备或指令：
  - 在前端只需要在 `ACTUATOR_DEVICES` 中增加一项，并填入 32 位十六进制字符串。
  - 推荐在后端/文档中保持一份与此表格一致的清单，方便校对。
- 如果需要从程序侧自动生成控制指令：
  - 可用 `packFrame + createPayload.*` 组合出控制帧；
  - 再用 `formatHex` 打印出来，与硬件侧定义逐字节对照。
